# Anticipated Judge Q&A

## "Is this actually working AI, or hardcoded demo data?"

It's real: the classifier is a genuinely trained model (transfer
learning, ImageNet -> RealWaste, `ai_model/train_classifier.py`),
evaluated on a held-out test split it never saw during training
(`ai_model/evaluate.py`). Upload any image live during the demo — the
prediction is computed on the spot, not looked up from a table. The
*sensor* data (bin fill history) is explicitly simulated and labeled as
such (see next question) — that distinction is deliberate and shown in
the UI, not hidden.

## "Why is the sensor/bin data simulated? Isn't that fake?"

Real IoT bin sensors weren't available for this hackathon prototype. The
simulation (`data_science/simulate_sensors.py`) is clearly labeled
`is_simulated=True` in the database schema and shown with a "Simulated
Data" badge everywhere it appears in the UI — never presented as a real
reading. Critically, the **prediction and priority-scoring models
themselves are real, trained models** operating on that data; swapping
the simulator for a real sensor feed requires zero changes downstream
(same `bin_sensor_readings` table, same feature engineering, same
models) — see `docs/ARCHITECTURE.md`.

## "What's your model's actual accuracy?"

The most recent training run: **89.0% accuracy / 89.2% macro F1** on
702 held-out test images across the 7 categories (weakest class "other"
at 84.6% F1 — the catch-all merge of Miscellaneous + Textile Trash;
strongest "organic" at 96.5%). Live number, generated by
`ai_model/evaluate.py` on a real held-out test split, viewable in the
Admin Panel -> "Classifier evaluation report" (never re-typed into a
slide by hand — see `docs/SIH_PRESENTATION.md`). Re-run
`python -m ai_model.evaluate` to reproduce.

## "Why didn't you fine-tune the object detector too?"

Fine-tuning a detector needs bounding-box-annotated waste images (not
just classification labels), and training a detector properly is
significantly more compute/time than fine-tuning a classifier —
impractical on CPU-only hardware in a hackathon timeframe. We used
pretrained YOLOv8n (COCO) for localization only, and were explicit about
that trade-off rather than overstating it — see `docs/LIMITATIONS.md`.
The architecture doesn't block this: swapping in a fine-tuned detector
later is a one-file change (`ai_model/detect.py`), nothing downstream
needs to change.

## "How does the system handle a wrong or uncertain prediction?"

Every classification below the configured confidence threshold
(`config/settings.yaml: ai.confidence_threshold`, default 0.55) is
hard-gated to "Unknown / Manual Verification Required" — the system
never auto-assigns a bin it isn't confident about. This gate is in one
place (`ai_model/inference_pipeline.py`), so there's no second code path
that could bypass it.

## "Why a 5-factor priority score instead of just fill percentage?"

A bin at 85% full in a low-footfall park is a different urgency than one
at 85% full outside a hospital that was last collected 3 days ago. The
weighted score (fill level, overflow probability, time since collection,
location importance, historical generation rate — all configurable in
`config/settings.yaml`) captures that; a flat threshold can't. The exact
breakdown per bin is visible on the Overflow Prediction page, not a
black-box number.

## "Is the route optimization provably optimal?"

No — it's a heuristic (sweep-clustering + nearest-neighbor + 2-opt),
which is standard and explainable for small/medium instances, not an
exact solver. We show the measured improvement over a naive baseline on
the same bin set live (Route Optimization / Waste Analytics pages)
rather than claiming optimality we can't back up. A production system
with hundreds of stops and hard constraints would move to OR-Tools —
noted explicitly in `docs/LIMITATIONS.md`.

## "How would this scale to a whole city?"

The architecture already supports it: SQLAlchemy models use portable
types so `database.url` is a one-line swap from SQLite to Postgres; the
route optimizer's vehicle count and the priority weights are runtime
config, not hardcoded; and the category/bin-color mapping is config, so
onboarding a new ward or city is a config change. See "Scalability" in
`docs/SIH_PRESENTATION.md`.

## "What about privacy — citizen photos might catch faces or people?"

Faces are blurred (real Haar-cascade detection) before any image is
written to disk — the pre-anonymization frame only exists in memory
during the request. Vehicle-plate blurring is included but explicitly
labeled as a best-effort heuristic, not a certified ANPR solution — see
`docs/LIMITATIONS.md: Privacy`.

## "What would it take to actually deploy this in a city?"

See `docs/DEPLOYMENT.md` for the free-tier hosting path (works today,
demonstrates the software is deployable), and the "Future Scope" section
of `docs/SIH_PRESENTATION.md` for what real IoT sensors, a fine-tuned
detector, and a routing-engine upgrade would add for a production pilot.

## "Can I see the raw evaluation numbers, not just a summary?"

Yes — `ai_model/evaluation_report.json` and
`data_science/models/prediction_metrics.json` are committed as real
generated artifacts, not summarized-away. The Admin Panel renders them
directly from those files.
